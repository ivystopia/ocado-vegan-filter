# Remaining whole-product implementation plan

Revised 2026-10-06. This is the execution plan for the unfinished development work, alongside [the active classifier specification](vegan-classifier-design.md). Updating this plan does not start another benchmark, change production models or activate catalogue classifications.

## Fixed policy

Keep canonical positive-reason precedence `tagged > manufacturer > name > ingredients`. Applicable manufacturer confirmation takes precedence over a vegan product name; do not weaken that precedence to fill the benchmark's scarce name-only cases. This orders supported positive reasons, not contradictory facts: correctly matched definite animal ingredients or animal processing still mean `nonvegan`, including when Ocado tags the product vegan. Retain those tag contradictions for reporting without contacting Ocado. Evidence belonging to the wrong product or unresolved material conflicts mean blocked `unknown`.

All four positive routes remain available. A positive claim must apply to the complete product, relevant variant, market and production period. Ordinary carrots and an unambiguous simple salad can qualify without a claim. Missing ingredients, absence of a recognised animal word, model agreement or a matching brand are insufficient by themselves.

## Current checkpoint

Both latest 96-case natural development pilots completed with 90 exact status matches, zero final unsafe positives, no operationally failed cases, and 22/24 eligible positives recovered. They have the same six status mismatches, including shared parser/gate issues and a coffee/filter scope question. Their manifests identify an implementation predating subsequent fixes. Neither run qualifies a model pair or validates the current working tree. GPT-6-Luna used fewer calls and output tokens in these runs, but quality must be checked again on the fixed candidate before selection.

The latest ordinary suite ran 183 tests with one failure and one live-test skip. The failure concerns negative-food identity/exclusion handling. Existing code changes and all historical benchmark results are preserved. No benchmark jobs remain running; the canonical database and embedded product ID sets have not been migrated.

## Ordered work and gates

1. **Settle material scope before tuning.** For food, the proposed default is the edible/drinkable product and relevant manufacturing/contact processes; assess sold non-food articles as complete articles. Do not demand proof of every external packaging material or invent unspecified glue risks. The treatment of supplied non-edible brewing filters/pods remains an explicit open boundary because the user has not selected an answer. Keep the coffee/filter case's original expectation and report the ambiguity; do not quietly relabel or omit it to obtain a pass. A sugar-cane fibre description is not evidence that refined-sugar processing applies. Resolve this boundary before it contributes to model qualification, then version any policy/fixture crosswalk.

2. **Finish implementation checks before further model calls.** Resolve the failing identity/exclusion test and validate the pending botanical-INCI and intentional-allergen changes. Test plant alternatives, flavour descriptions, recipe books, precautionary allergens, definite animal foods and animal/tag contradictions together. Check scoped manufacturer evidence from typed product information as well as websites, wrong variants, stale bindings and both agreeing passes. Run the ordinary suite, userscript syntax and diff checks. A failing deterministic, validation, persistence, export or browser contract blocks model qualification. Offline replays can diagnose a fix but do not replace fresh final validation.

3. **Audit development references and scoring separately.** Attribute each mismatch to policy ambiguity, extraction/rules, validation/merging, model reasoning, operational failure or reference error. Validate required issue codes against the actual mechanism and permit equivalent explanations only through an explicit, tested rubric revision. Preserve old expectations/results and publish corrections with evidence and a crosswalk; never relax a requirement merely because a candidate fails it. Automated source-backed readings are reference evidence with disclosed limitations, not independent human gold or a guarantee about hidden manufacturing. Keep the locked set out of tuning. Retain the 240/360 natural-case targets and report current shortfalls; synthetic siblings cannot fill them.

4. **Compare inexpensive primary candidates on a fixed revision.** After steps 1–3, run the same small regression controls, then the same frozen 96-case pilot for GPT-5.6-Luna/high and GPT-6-Luna/high. Expand qualifying candidates to the complete development set. Preserve raw model decisions and gated results separately. Count every call, retry, input/cache/output token, disagreement, arbitration call and latency; reasoning is already part of output usage. Start a new result directory when code, prompts, policy or fixtures change. Resume only identical configurations, checkpoint at included-plan limits and use no paid/API fallback.

5. **Prevent inappropriate expensive-primary escalation.** Update the comparison runner so two failed pipelines do not automatically justify GPT-6.1-Sol/medium as primary. First require an attributed failure review showing that both inexpensive models fail a settled policy on correct inputs with functioning rules/gates. Shared implementation defects, defective references, incomplete quotas and unresolved scope require repair, not a model upgrade. Prefer the least costly candidate satisfying the same safety and usefulness gates; historical smoke tests alone cannot justify switching defaults.

6. **Select arbitration and validate the complete pair.** Compare GPT-6.1-Sol/medium, GPT-6.1-Sol/high and GPT-6-Astra/medium using balanced development cases with supported positives, unknowns and negatives, plus actual primary disagreements. Preserve exactly two fresh independent primary calls, exactly two blind fresh arbitration calls only for raw status/reason disagreement, no escalation of agreed unknowns and no recursion. Complete the natural quotas before release qualification. Evaluate the fixed selected pipeline on the untouched locked set for three recorded repetitions and the 200-case uniform workload. Require zero final unsafe positives, at least 98% positive recall and at least 29/30 per positive route each locked repetition, mandatory controls and complete evidence/protocol/export/browser contracts. Report every failure; do not choose the best repetition. Present the recommended pair and measured usage to the user before canonical reclassification.

7. **Validate migration in isolation before activation.** Refresh the read-only impact preview against the final code, distinguish all-known from stored-current products, and produce tag/animal reports separately from identity conflicts. After model selection, use a WAL-consistent shadow snapshot; revalidate existing positives with conclusive cheap rules first and only necessary semantic cases through the chosen pair. Review promotions, tag contradictions and stratified demotions, retain before/after decisions and audit linkage, and perform the planned uniform 600-positive audit on the fixed shadow candidate. Disclose automated-reference and sampling limitations rather than claiming an unconditional physical guarantee. Canonical activation, generated allowlists and release work remain gated by the user's decision and the existing runbooks. Preserve safety exclusions during rollback.

## Completion evidence

The handoff must contain the final code/policy/prompt/schema/fixture versions, passing implementation checks with explicit skips, unchanged or documented reference crosswalks, a qualified model-pair comparison with complete usage, locked-run outcomes, shadow transitions, the positive audit and reportable Ocado contradictions. Keep development commits local on `dev`. This plan does not authorise a release, push, installed FireMonkey update or message to Ocado.
